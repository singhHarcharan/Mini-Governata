The mission

Learn the system by growing it.

You will build a small data-governance product containing assets, approval tasks, policies, evidence, audit history, and background processing. We begin in your strongest area, React, then replace mocks with a Go API, then add database and distributed-system boundaries one at a time.

End state: when you see a Governata screen, you can trace it from the React interaction through its API contract, middleware, Go handler, service, repository, database operation, event publication, and consumer.

Learning rules

One new difficultyAdd only one unfamiliar architectural idea per phase.
Visible result firstEvery phase must change something you can see or test.
Trace every featureAlways write the full frontend-to-storage execution path.
Earn complexityDo not add NATS, Redis, or Kubernetes before their problem exists.

Turn a large codebase into a sequence of small, searchable contracts.

2–3 sessionsNavigationArchitecture 0%
Outcome: you can explain one Governata request from click to database.

Purpose

Remove the feeling that Go code is disconnected. Learn which transitions are symbol calls and which are HTTP, message, database, or interface contracts.

What you will produce

A handwritten execution map for “Complete task” and a glossary of 25 Go/platform terms in your own words.

Learn vs. master

Learn nowGo modules, packages, exported names, method receivers, routes, handlers, interfaces, repositories, NATS subjects.
Master by the gateSearch by URL or subject when Command-click cannot cross a runtime boundary.

Guided code-reading order

TasksPage.tsx
  → api/governance.ts (POST /tasks/:id/complete)
  → api/router.go (route registration)
  → handlers/tasks.go (CompleteTask)
  → workflow/engine.go (UpdateTaskStatus)
  → store/pg/tasks.go (model/repository)
  → migrations/001_schema.up.sql (table)

1

Frontend-only governance workspace

Start from React confidence and build the product language before any backend exists.

4–6 sessionsReactTypeScriptTanStack Query 0%
Outcome: a polished UI that behaves like a real app using a mock API.

What are we creating?

A React workspace for data assets and stewardship tasks. Users browse assets, inspect details, filter tasks, and complete an approval workflow. Mock Service Worker acts as the temporary backend.

Why this phase exists

You already know React. We first define the screens, domain vocabulary, API shapes, loading states, and errors. When Go arrives, the frontend becomes an executable specification.

Learn vs. master

Learn nowDomain modeling, API boundaries, Zod validation, MSW, query keys, mutations, invalidation, feature-based folders.
Master by the gateSeparating server state from UI state; building screens that never import mock data directly.

Folder structure

mini-governata/
└── apps/web/
    ├── src/
    │   ├── app/              # router, providers, app shell
    │   ├── features/
    │   │   ├── assets/       # pages, components, hooks, schemas
    │   │   └── tasks/
    │   ├── api/              # fetch client and endpoint functions
    │   ├── mocks/            # MSW handlers and seed factories
    │   ├── shared/           # reusable UI, errors, utilities
    │   └── test/
    ├── package.json
    └── vite.config.ts

Features

  • Asset list and detail pages
  • Task list, filters, detail drawer
  • Complete/cancel actions
  • Loading, empty, error states
  • Responsive navigation

Do not add yet

No Go, database, auth, Docker, NATS, Redis, MinIO, or microservices. The goal is a clean frontend contract, not infrastructure.

Build checklist

Definition of done

A user can browse mock assets, open a task, complete it, and immediately see the updated state. Refreshing resets data because persistence intentionally does not exist yet.

4

Interfaces and clean backend boundaries

Make Go navigation predictable through explicit dependency direction.

3–5 sessionsInterfacesDependency injection 0%
Outcome: handlers depend on behavior, not database details.

Purpose

Learn why “Go to Definition” may land on an interface. Go interfaces are satisfied implicitly, and constructors wire a concrete implementation at runtime.

Product increment

Refactor the working API without changing behavior. Add isolated handler, service, and repository tests.

Concepts

Learn nowSmall consumer-owned interfaces, implicit satisfaction, constructor injection, dependency inversion, compile-time interface assertions, test doubles.
Master by the gateUse Go to Implementations and trace concrete construction back to main.go.

Target dependency direction

cmd/api → router → handler → service → repository interface
                                      ↑
                         memory repository implements it

Rules:
• domain imports nothing from api or storage
• service never imports Gin
• handler never runs a database query
• main.go owns concrete dependency wiring

Build checklist

Definition of done

You can swap the repository implementation in main.go without modifying handlers or services.

6

Authentication, tenants, and permissions

Teach every request who the user is, which tenant owns the data, and what action is allowed.

5–8 sessionsOIDC/JWTRBACSecurity 0%
Outcome: tenant A can never read or mutate tenant B’s records.

Purpose

Reproduce the protected-route chain used throughout Governata: authenticate, resolve tenant, authorize permission, then run business logic.

Product increment

Login, current-user display, viewer/steward/admin roles, tenant-scoped queries, permission-aware buttons, and 401/403 handling.

Concepts

Learn nowOIDC, JWT claims, middleware ordering, context values, RBAC, fail-closed checks, tenant query scoping, frontend route guards.
Master by the gateProve authorization in the backend even when the frontend hides controls.

Required middleware order

request ID → recovery → authentication → tenant resolution
→ permission check → handler → service → tenant-scoped repository

Build checklist

Definition of done

Automated tests prove cross-tenant reads and writes fail. Changing a role changes both visible UI actions and backend authorization.

5–7 sessionsState machineAuditTime 0%

Purpose

Model the Governance task engine: controlled transitions, task templates, immutable history, due times, SLA breaches, comments, assignment, and escalation.

Timeline UI, allowed-action buttons, SLA badges, “My tasks,” overdue filters, task templates, and bulk assignment.

Concepts

8

Split Core and Governance with NATS

Introduce a service boundary only after the monolith is understood.

6–9 sessionsNATSEventsService isolation 0%
Outcome: Core owns assets; Governance consumes and annotates them.

Purpose

Understand Governata’s “modules are islands” rule. Core owns the canonical asset. Governance stores its projection and business annotations, linked by platform_asset_id.

Product increment

A new Core service creates assets. Governance receives asset-created events and automatically creates its local projection.

Concepts

Learn nowNATS subjects, publish/subscribe, request-reply, JetStream consumers, durable names, queue groups, event envelopes, correlation IDs, eventual consistency.
Master by the gateTrace publisher → subject → stream → durable consumer → local projection.

Target structure

services/
├── core/
│   ├── cmd/api/main.go
│   ├── internal/assets/
│   └── migrations/
├── governance/
│   ├── cmd/api/main.go
│   ├── cmd/worker/main.go
│   ├── internal/projection/
│   └── migrations/
└── shared-sdk/
    ├── subjects/
    └── messaging/

New term

Eventual consistency means the source changes first and other views catch up shortly afterward. The UI must represent “processing” rather than pretending all services update atomically.

Ownership rule

No cross-service database joins, no Governance writes to Core tables, and no copied subject strings outside the shared registry.

Build checklist

Definition of done

Creating an asset in Core causes a Governance projection without direct database access or backend-to-backend HTTP.

9

Reliable events: outbox, idempotency, and retries

Make message delivery safe when processes crash or messages arrive twice.

5–8 sessionsOutboxIdempotencyWorkers 0%
Outcome: crashes and duplicate delivery do not lose or duplicate business effects.

Purpose

A database write can succeed while event publication fails. The outbox pattern writes the business change and pending event in one transaction, then a relay publishes later.

Product increment

Durable publication, duplicate-safe consumers, retries with backoff, dead-letter handling, and an operations screen for failed messages.

Concepts

Learn nowOutbox/inbox tables, idempotency keys, at-least-once delivery, retry backoff, dead-letter queues, worker pools, goroutines, channels, select, context cancellation.
Master by the gateDesign handlers so processing the same event twice produces the same final state.

Build checklist

Definition of done

Automated failure tests prove no event is lost after a crash and duplicate delivery creates no duplicate projection or task.

10

Policies with CEL

Let users express governance rules without compiling Go code.

4–6 sessionsCELValidationPolicy engine 0%
Outcome: policies can be drafted, validated, published, and evaluated.

Purpose

Recreate Governata’s policy-engine pattern using Common Expression Language, a safe expression language for evaluating rules against structured context.

Example rule

asset.sensitivity == "restricted"
  ? user.role in ["steward", "admin"]
  : true

Concepts

Learn nowParse/compile/evaluate lifecycle, typed environments, validation diagnostics, policy versioning, draft/published/retired states, safe evaluation limits.
Master by the gateKeep user expressions constrained, validated, versioned, and auditable.

Build checklist

Definition of done

A user can safely test and publish a policy, and every evaluation states which immutable version produced the result.

11

Redis, evidence files, and background work

Add cache and object storage where relational storage is not the right tool.

5–8 sessionsValkey/RedisMinIOConcurrency 0%
Outcome: users attach evidence and workers process it safely.

Purpose

Store file bytes in MinIO, file metadata in PostgreSQL, and short-lived computed results in Redis/Valkey. Use workers for expensive processing.

Product increment

Evidence upload/download, presigned URLs, checksums, a cached dashboard summary, file-processing jobs, and progress display.

Concepts

Learn nowMultipart upload, streams, checksums, S3-compatible APIs, presigned URLs, cache-aside, TTL, invalidation, distributed locks, bounded worker concurrency.
Master by the gateChoose PostgreSQL, object storage, or cache based on ownership and durability needs.

Security focus

Limit file size, sanitize names, verify content type, isolate tenant object keys, never trust client checksums, and keep presigned URLs short-lived.

Reliability focus

A cache miss must be correct, only slower. A failed file job must be retryable without creating duplicate metadata.

Build checklist

Definition of done

Files are tenant-isolated, metadata remains correct after retries, and disabling Redis affects speed rather than correctness.

The repeatable study loop

Use this for every feature.

  1. Predict the execution path before opening code.
  2. Run the smallest test or request that proves the behavior.
  3. Trace component → client → route → handler → service → store → event.
  4. Change one rule and update its closest test first.
  5. Break one dependency and observe the failure state.
  6. Explain the flow aloud without the editor.

Pacing

Move by evidence, not dates.

Session estimates are guides, not deadlines. Do not advance because a week ended. Advance when the definition-of-done gate is true.

If a phase becomes frustrating, shrink the current task until it produces a visible result in one sitting. Never respond by adding another framework.

Mini Governata is not a throwaway tutorial. It is your controlled laboratory for understanding the production platform.
