Security principle

The frontend improves experience; the backend enforces authority. Every protected operation must derive identity from a validated token, resolve a trusted tenant, check permission, and scope storage—then audit the decision.

JWT

A signed token is claims, not trust by itself

A JWT has header, payload, and signature. The payload is encoded, not encrypted. Validate:

  • signature using an allowed algorithm and trusted key;
  • iss (issuer) and aud (intended audience);
  • exp and optionally nbf, with small clock skew;
  • required subject/identity claims;
  • key rotation via key ID/JWKS caching.
Never accept alg: none, never choose verification behavior from untrusted claims, and never log whole tokens.

type Principal struct {
    UserID string
    TenantID string
    Roles []string

func Require(permission Permission) gin.HandlerFunc {
    return func(c *gin.Context) {
        p, ok := PrincipalFromContext(c.Request.Context())
        if !ok { c.AbortWithStatus(http.StatusUnauthorized); return }
        if !Allows(p.Roles, permission) {
            c.AbortWithStatus(http.StatusForbidden); return
        }
        c.Next()
    }
}

Use private typed context keys. Store a small immutable principal, not request objects or database handles. Do not trust tenantId from a JSON body without verifying the principal’s membership.

RBAC

Roles group permissions; code checks permissions

const (
    ViewAssets Permission = "assets:view"
    CreateTask Permission = "tasks:create"
    CompleteTask Permission = "tasks:complete"
)

var grants = map[Role]map[Permission]bool{
    Viewer: {ViewAssets: true},
    Editor: {ViewAssets: true, CreateTask: true, CompleteTask: true},
    Admin:  {ViewAssets: true, CreateTask: true, CompleteTask: true},
}

Endpoints ask for a permission, not a hard-coded role name. This lets role composition evolve. Default deny: an unknown role or permission grants nothing. Add ownership/resource checks when roles alone are insufficient.

401

Identity is absent or invalid. Re-authentication may help.

403

Identity is known but lacks authority. Logging in again should not change it.

Tenant isolation

Defend at multiple layers

  1. Transport: trusted middleware resolves tenant membership.
  2. Application: tenant ID is a required use-case argument.
  3. Repository: every lookup/write filters by tenant.
  4. Schema: tenant-aware unique keys and foreign relationships.
  5. Tests: cross-tenant IDs return no data and make no changes.
// Good: impossible to "forget" tenant at call sites.
FindTask(ctx context.Context, tenantID, taskID string) (*Task, error)

// Dangerous: ID-only lookup can leak across tenants.
FindTask(ctx context.Context, taskID string) (*Task, error)

Frontend

Guide the user without pretending to secure the API

  • Centralize token attachment and 401 handling in the API client.
  • Render permissions from a session model to avoid offering impossible actions.
  • Still handle 403 because permissions can change or resource rules can differ.
  • Avoid long-lived tokens in insecure storage; follow the chosen identity architecture.
  • Never embed secrets in Vite environment variables—they ship to the browser.

Knowledge check

1. Does decoding a JWT validate it?

Show answer
No. Anyone can encode claims. Trust requires signature, issuer, audience, time, and algorithm validation.

2. Why permission checks instead of role checks at endpoints?

Show answer
Permissions express required capability; role-to-permission composition can change without rewriting endpoint policy.

3. Why might cross-tenant access return 404?

Show answer
It avoids revealing that a resource exists in another tenant while still denying access.
