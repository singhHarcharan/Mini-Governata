Build the Mini Governata workspace in familiar React territory

What you will build

A user can browse data assets, search and filter them, open an asset detail page, create a governance task, move it through allowed statuses, and view an audit-like timeline. Refreshing the page still behaves like a server because requests are intercepted by a mock API.

Domain first

Model the nouns and verbs

export type Asset = {
  id: string
  name: string
  kind: 'table' | 'dashboard' | 'pipeline'
  owner: string
  description: string
  classification: 'public' | 'internal' | 'confidential'
}

export type TaskStatus = 'pending' | 'in_progress' | 'completed'

export type GovernanceTask = {
  id: string
  assetId: string
  title: string
  status: TaskStatus
  assignee?: string
  createdAt: string
}

Types are not decoration; they are the first version of the contract Go will later implement. Use domain names in code and UI. Avoid vague containers such as data, item, or thing.

Nouns

Asset, Task, User, AuditEntry. They become types, API resources, and later database tables.

Verbs

List assets, inspect asset, create task, start task, complete task. They become use cases and endpoints.

Architecture

Organize by feature, keep boundaries visible

src/
├── app/                 # router, providers, app shell
├── features/
│   ├── assets/
│   │   ├── api.ts       # HTTP-shaped functions
│   │   ├── components/
│   │   ├── queries.ts   # server-state hooks
│   │   ├── schemas.ts   # runtime response validation
│   │   └── types.ts
│   └── tasks/
├── mocks/               # MSW handlers + in-memory data
├── shared/              # generic UI/utilities only
└── test/                # test setup and helpers

A feature owns its domain-specific API calls, UI, queries, and types. shared is for genuinely reusable primitives—not a dumping ground. This mirrors backend modularity later.

State model

Separate server state from UI state

Rule: do not copy query data into useState. Two sources of truth drift. Keep remote data in the query cache and derive views from it.
export const taskKeys = {
  all: ['tasks'] as const,
  list: (filters: TaskFilters) => [...taskKeys.all, 'list', filters] as const,
}

export function useTasks(filters: TaskFilters) {
  return useQuery({
    queryKey: taskKeys.list(filters),
    queryFn: () => taskApi.list(filters),
  })
}

Query keys are cache addresses. Stable key factories make invalidation predictable and later reveal which backend resource a screen depends on.

Contracts

Types disappear at runtime; schemas do not

const AssetSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1),
  kind: z.enum(['table', 'dashboard', 'pipeline']),
  owner: z.string(),
  description: z.string(),
  classification: z.enum(['public', 'internal', 'confidential']),
})

const AssetsResponseSchema = z.array(AssetSchema)

export async function listAssets(): Promise<Asset[]> {
  const response = await fetch('/api/assets')
  if (!response.ok) throw new Error(`Request failed: ${response.status}`)
  return AssetsResponseSchema.parse(await response.json())
}

TypeScript trusts your annotation, but the network can return anything. Zod converts an assumed contract into a checked contract. Later, Go DTOs and validation form the server half.

Mock boundary

Mock HTTP, not imported functions

const tasks: GovernanceTask[] = []

export const handlers = [
  http.get('/api/assets', () => HttpResponse.json(assets)),

  http.post('/api/tasks', async ({ request }) => {
    const input = CreateTaskSchema.parse(await request.json())
    const task = { id: crypto.randomUUID(), status: 'pending',
      createdAt: new Date().toISOString(), ...input }
    tasks.push(task)
    return HttpResponse.json(task, { status: 201 })
  }),
]

MSW lets the application make real fetch calls while a service worker supplies responses. When Go arrives, the UI contract remains stable; only the request destination changes.

Mutations

Make write behavior explicit

const completeTask = useMutation({
  mutationFn: (taskId: string) => taskApi.complete(taskId),
  onSuccess: () => queryClient.invalidateQueries({ queryKey: taskKeys.all }),
})

A mutation is not merely “POST.” It includes pending UX, error UX, success reconciliation, and double-submit protection. Disable the button while pending and show an actionable error without discarding the existing screen.

Deep dive: invalidation or optimistic update?

Begin with invalidation: after success, refetch authoritative data. Optimistic updates feel faster but require rollback and concurrency reasoning. Add them only after the basic contract is correct.

UX states

Every data screen has more than a happy path

Loading

Preserve layout; communicate that work is ongoing.

Empty

Explain why nothing exists and provide a next action.

Error

Keep context, use plain language, offer retry.

Also design stale/refetching state, disabled actions, success feedback, keyboard focus after modals, accessible labels, and narrow mobile layouts.

Testing

Test behavior at the boundary users see

it('completes a pending task', async () => {
  renderApp('/tasks')
  const user = userEvent.setup()

  await user.click(await screen.findByRole('button', { name: /complete/i }))

  expect(await screen.findByText(/completed/i)).toBeVisible()
})

Prefer roles and accessible names over CSS selectors. Let MSW exercise the HTTP-shaped contract. Add one schema-failure test so a malformed response becomes an intentional error state.

Implementation sequence

  1. Scaffold Vite + React + TypeScript and the app shell.
  2. Create domain types and Zod schemas.
  3. Add React Router: assets list, asset detail, tasks.
  4. Implement MSW read endpoints and query hooks.
  5. Build loading, empty, error, and populated states.
  6. Add create/start/complete task mutations.
  7. Add task timeline and asset-task relationship.
  8. Test the main user flow and one failure per screen.
Vertical-slice rule: finish one thin user journey—list assets → view asset → create task—before decorating all pages.

Knowledge check

1. Why use MSW instead of importing a mock listAssets()?

Show answer
MSW preserves the network boundary, so the component, query hook, fetch behavior, status handling, and runtime parsing remain the same when Go replaces the mock.

2. Where should selected asset ID live?

Show answer
Usually in the URL route because it identifies the page, supports refresh/deep linking, and should be shareable.

3. What must happen after a successful task mutation?

Show answer
The UI cache must reconcile with server truth—initially by invalidating/refetching relevant task queries—and pending/error/success states must be represented.

Common traps

  • Building a global state store before deciding which state is remote, URL, local, or derived.
  • Sharing generated-looking components instead of domain concepts.
  • Typing API JSON without validating it at runtime.
  • Testing implementation details rather than user behavior.
  • Perfecting the dashboard before one complete mutation flow works.
