Relational model

The database is a second guardian of truth

CREATE TABLE assets (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  name text NOT NULL,
  kind text NOT NULL CHECK (kind IN ('table','dashboard','pipeline')),
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE governance_tasks (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  asset_id uuid NOT NULL REFERENCES assets(id),
  title text NOT NULL CHECK (length(title) BETWEEN 3 AND 120),
  status text NOT NULL CHECK (status IN ('pending','in_progress','completed')),
  created_at timestamptz NOT NULL,
  updated_at timestamptz NOT NULL
);
CREATE INDEX idx_tasks_tenant_status ON governance_tasks(tenant_id, status);

A primary key identifies a row. A foreign key protects relationships. NOT NULL distinguishes required facts. Checks block invalid categories. Indexes accelerate specific lookup patterns but add write/storage cost.

Tenant-safe uniqueness: decide whether a name is globally unique or unique inside a tenant. Most SaaS constraints should include tenant_id.

Migrations

Schema is ordered history

migrations/
├── 001_create_assets.up.sql
├── 001_create_assets.down.sql
├── 002_create_tasks.up.sql
└── 002_create_tasks.down.sql

A migration is a reviewed, repeatable state transition for the database. Apply migrations in CI/deployment, not by silently running ORM auto-migration at application startup. Prefer expand/contract for breaking changes: add compatible schema, deploy code using it, backfill, then remove old schema later.

Deep dive: safe column rename
  1. Add the new column.
  2. Deploy code that writes both old and new.
  3. Backfill existing rows.
  4. Deploy code reading only new.
  5. Remove old after every instance is compatible.

GORM mapping

ORM convenience does not replace SQL understanding

type taskRow struct {
    ID        uuid.UUID `gorm:"type:uuid;primaryKey"`
    TenantID  uuid.UUID `gorm:"type:uuid;not null;index:idx_tasks_tenant_status"`
    AssetID   uuid.UUID `gorm:"type:uuid;not null"`
    Title     string    `gorm:"not null"`
    Status    string    `gorm:"not null;index:idx_tasks_tenant_status"`
    CreatedAt time.Time `gorm:"not null"`
    UpdatedAt time.Time `gorm:"not null"`
}

func (taskRow) TableName() string { return "governance_tasks" }

Keep database row types inside the adapter and map them to domain types. This prevents GORM tags, nullable wrappers, and association behavior from leaking inward.

func (s *TaskStore) Find(ctx context.Context, tenantID, id string) (*task.Task, error) {
    var row taskRow
    err := s.db.WithContext(ctx).
        Where("tenant_id = ? AND id = ?", tenantID, id).
        First(&row).Error
    if errors.Is(err, gorm.ErrRecordNotFound) { return nil, task.ErrNotFound }
    if err != nil { return nil, fmt.Errorf("find task: %w", err) }
    return toDomain(row), nil
}

Always attach the request context. Always scope tenant-owned queries. Translate adapter errors into domain/application categories.

Transactions

All or nothing for one invariant

err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
    var row taskRow
    if err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).
        Where("tenant_id = ? AND id = ?", tenantID, id).First(&row).Error; err != nil {
        return err
    }
    domain := toDomain(row)
    if err := domain.Complete(); err != nil { return err }
    return tx.Model(&row).Updates(map[string]any{
        "status": domain.Status, "updated_at": clock.Now(),
    }).Error
})

A transaction groups database statements atomically. A row lock prevents two transactions from simultaneously validating the same old state. Keep transactions short; do not call slow external services while locks are held.

Queries

Pagination and indexes are one design decision

query := db.WithContext(ctx).Where("tenant_id = ?", tenantID)
if filter.Status != "" { query = query.Where("status = ?", filter.Status) }
if filter.After != nil {
    query = query.Where("(created_at, id) < (?, ?)", filter.After.Time, filter.After.ID)
}
err := query.Order("created_at DESC, id DESC").Limit(limit + 1).Find(&rows).Error

Cursor pagination remains stable as rows are inserted. Use a deterministic tiebreaker such as ID. Cap page size on the server. Create indexes that match tenant filter plus ordering/filter fields, then inspect query plans when performance matters.

Connections and nulls

Production details begin here

  • Configure a bounded connection pool; each app instance multiplies total connections.
  • Use timestamptz and store instants in UTC.
  • Represent optional database values explicitly (*string or sql.NullString), then map to domain meaning.
  • Use JSONB for genuinely flexible documents, not as an escape from relational design.
  • Log slow operations with context but never secrets or full sensitive payloads.

Build sequence

  1. Draw entities and relationships before writing GORM structs.
  2. Write up/down migrations and apply to a clean database.
  3. Create private row models and mapping functions.
  4. Implement repository methods with tenant predicates and context.
  5. Add transaction-protected task transitions.
  6. Add filter + bounded pagination.
  7. Run adapter integration tests against PostgreSQL.
  8. Restart the service and prove state remains.

Knowledge check

1. Why keep both domain validation and database constraints?

Show answer
Domain checks give meaningful behavior before writes; constraints protect truth against bugs, concurrency, scripts, and other writers.

2. Why not make network calls inside a transaction?

Show answer
They prolong locks and increase contention/failure uncertainty. Persist an outbox record inside the transaction and publish later (Phase 9).

3. What must every tenant-owned query include?

Show answer
A trusted tenant predicate, ideally reinforced by repository APIs and later database policies—not a tenant supplied casually by the request body.
