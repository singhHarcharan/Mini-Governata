Types

Make invalid ideas harder to express

type Status string

const (
    StatusPending    Status = "pending"
    StatusInProgress Status = "in_progress"
    StatusCompleted  Status = "completed"
)

type Task struct {
    ID        string
    Title     string
    Status    Status
    CreatedAt time.Time
}

Status is a distinct named type, not a free-form string. Constants enumerate meaningful values. Go has no classes: a struct holds data; methods add behavior; packages group related code.

TypeScript

  | 'pending'
  | 'in_progress'
  | 'completed'

Values, pointers, and mutation

func (t Task) Label() string {       // copy; reading is natural
    return t.Title + " [" + string(t.Status) + "]"
}

func (t *Task) Complete() error {    // pointer; changes this task
    if t.Status != StatusInProgress {
        return ErrInvalidTransition
    }
    t.Status = StatusCompleted
    return nil
}

Use a pointer receiver when mutating or when the struct is expensive to copy. Be consistent for a type. A pointer may be nil; a struct value has usable zero-valued fields.

Collections and control flow

Read Go’s deliberately small language

tasks := []Task{}                    // slice
byID := map[string]*Task{}           // map

for _, task := range tasks {
    if task.Status == StatusPending {
        fmt.Println(task.Label())
    }
}

switch command {
case "list":
    list(tasks)
case "complete":
    complete(byID[id])
default:
    return fmt.Errorf("unknown command %q", command)
}

A slice is a window over an underlying array; append may return a new slice header, so assign its result. Map lookup can return a second boolean: task, ok := byID[id]. Go has one loop keyword, for.

Deep dive: slice aliasing

Two slices may share an underlying array. Mutating an element can be visible through both. Appending can reallocate and break that sharing. Treat slices as small descriptors—not as immutable JavaScript arrays.

Errors

Failures are explicit data

var ErrNotFound = errors.New("task not found")

func (s *MemoryStore) Find(id string) (*Task, error) {
    task, ok := s.tasks[id]
    if !ok { return nil, fmt.Errorf("find task %s: %w", id, ErrNotFound) }
    return task, nil
}

task, err := store.Find(id)
if errors.Is(err, ErrNotFound) { /* expected category */ }
if err != nil { /* unexpected failure */ }

Wrap errors with %w to add operation context while preserving their identity for errors.Is. Avoid comparing error strings. Return errors; log them at a boundary that knows context, otherwise duplicate logs appear.

panic is not ordinary error handling. Reserve it for truly unrecoverable programmer/startup conditions. User input, missing tasks, and invalid transitions return errors.

Interfaces

Let consumers describe the capability they need

type Store interface {
    Create(task Task) error
    Find(id string) (*Task, error)
    List() []Task
}

type Service struct { store Store }

func NewService(store Store) *Service { return &Service{store: store} }

The service depends on behavior, not the map implementation. Interfaces are satisfied implicitly. Keep them small and define them close to the consuming package. Phase 4 will turn this into the full architecture.

Tests

Use tables to prove rules, not lines

func TestTaskComplete(t *testing.T) {
    tests := []struct {
        name    string
        initial Status
        wantErr bool
    }{
        {"from in progress", StatusInProgress, false},
        {"from pending", StatusPending, true},
        {"already completed", StatusCompleted, true},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            task := Task{Status: tt.initial}
            err := task.Complete()
            if (err != nil) != tt.wantErr { t.Fatalf("error = %v", err) }
        })
    }
}

Each row states a business example. Tests live in *_test.go, use TestXxx, and receive *testing.T. Run go test -race ./... when concurrency appears.

  3. Write transition tests before CLI wiring.
  4. Create a Store interface and memory implementation.
  5. Create a service for create/start/complete behavior.

  8. Format, test, run, and deliberately trigger every error.

Knowledge check

1. Why must append be assigned?

Show answer
It returns an updated slice header and may allocate a new underlying array; ignoring the return can lose the new length/storage.

2. When use *Task?

Show answer
When the function/method must mutate the same task, represent absence with nil, or avoid copying a substantial value. Do not use pointers automatically for every value.

3. Why wrap with %w?

Show answer
It adds useful operation context while allowing callers to recognize the original error using errors.Is or errors.As.

Common traps

  • Writing Java-style getters, setters, and giant interfaces.
  • Ignoring returned errors or logging the same error in every layer.
  • Returning pointers to loop variables without understanding their lifetime/identity.
  • Using strings everywhere instead of small domain types.
  • Putting all code in main.go, making rules hard to test.
