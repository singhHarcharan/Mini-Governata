Split Core and Governance without creating a distributed monolith

Give services clear ownership, connect them with NATS/JetStream contracts, and make eventual consistency visible in both code and UX.

What you will build

Core owns canonical assets. Governance owns tasks and an asset projection needed for its screens. Core publishes asset events; Governance consumes them durably. Governance can request current asset details when synchronous truth is required.

Ownership

A service owns its data and decisions

Core serviceGovernance service
Canonical asset identity and metadataGovernance tasks, transitions, policies, audit
Publishes asset lifecycle factsMaintains an asset projection for its use cases
Answers asset queriesDoes not update Core tables directly

Do not share one repository across services or join across each other’s tables. A service boundary is meaningful only if its owner can protect invariants independently.

NATS modes

Choose communication from the required semantics

ModeUseTradeoff
Core pub/subEphemeral fan-out notificationsOffline subscriber misses messages.
Request/replyImmediate question with bounded responseCaller and responder are temporally coupled.
JetStreamDurable events, replay, acknowledged processingRequires consumer, retention, retry, and idempotency design.

Use request/reply when the user cannot proceed without a current answer. Use durable events to distribute facts that consumers may process later.

Event contract

An event states a past fact

type Envelope[T any] struct {
    ID            string    `json:"id"`
    Type          string    `json:"type"`
    Version       int       `json:"version"`
    TenantID      string    `json:"tenantId"`
    OccurredAt    time.Time `json:"occurredAt"`
    CorrelationID string    `json:"correlationId"`
    CausationID   string    `json:"causationId,omitempty"`
    Data          T         `json:"data"`
}

type AssetCreatedV1 struct { ID, Name, Kind, Owner string }

asset.created.v1 is a fact. create.asset is a command. Version schemas deliberately. IDs support deduplication; correlation joins one business flow; causation points to the message/request that triggered this event.

Do not publish internal database structs. Consumers will accidentally depend on fields you never promised.

Subjects and consumers

Names route messages; configuration defines durability

// Examples—not magic strings scattered through handlers.
core.asset.created.v1
core.asset.updated.v1
governance.task.completed.v1

msg, err := js.Publish(ctx, "core.asset.created.v1", payload)

consumer, err := js.CreateOrUpdateConsumer(ctx, "CORE_EVENTS", jetstream.ConsumerConfig{
    Durable: "governance-assets-v1",
    FilterSubject: "core.asset.*.v1",
    AckPolicy: jetstream.AckExplicitPolicy,
})

A stream persists selected subjects. A durable consumer remembers progress. Explicit acknowledgement means “processing succeeded.” Redelivery means duplicates are normal. Queue groups distribute work among replicas; they do not turn processing into exactly-once effects.

Handler discipline

Acknowledge only after a durable effect

func handleAssetCreated(ctx context.Context, msg jetstream.Msg) {
    event, err := decodeAndValidate(msg.Data())
    if err != nil { msg.Term(); return }          // poison contract; inspect/DLQ
    if inbox.Seen(ctx, event.ID) { msg.Ack(); return }

    if err := projection.Apply(ctx, event); err != nil {
        msg.Nak()                                  // retry later
        return
    }
    msg.Ack()
}

Decode, validate, deduplicate, apply, then acknowledge. Permanent schema errors and transient database errors need different treatment. Phase 9 makes the reliability machinery explicit.

Governata connection

Read the platform as islands plus contracts

Governata’s design treats modules as islands and NATS as the nervous system. When tracing across modules:

  1. Find the subject constant or event type in the publisher.
  2. Find stream/consumer registration and filtered subjects.
  3. Find the message handler.
  4. Trace from decoded payload into application service/projection.
  5. Inspect acknowledgment and failure behavior.

Direct source navigation stops at publish because the receiver is chosen by broker configuration at runtime.

Build sequence

  1. Write an ownership table: data, commands, events, and queries per service.
  2. Move canonical assets into Core; keep tasks in Governance.
  3. Define versioned envelopes and subject constants.
  4. Publish asset events and configure a durable stream.
  5. Build Governance’s idempotent asset projection consumer.
  6. Add request/reply for one truly synchronous lookup with timeout.
  7. Expose projection lag/syncing behavior in React.
  8. Stop Governance, publish events, restart it, and prove catch-up.

Knowledge check

1. Does message acknowledgement guarantee exactly-once business effects?

Show answer
No. A crash after the database write but before ack causes redelivery. The handler must be idempotent.

2. When use request/reply?

Show answer
For a bounded synchronous question whose answer is required now, with explicit timeout and failure behavior—not as a hidden replacement for every function call.

3. Why maintain a projection?

Show answer
Governance can serve its use cases without querying Core for every read while respecting Core’s ownership. The tradeoff is observable lag.
