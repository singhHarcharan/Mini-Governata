Implicit interfaces

Implementation is structural

// application package: the consumer owns this interface
type TaskRepository interface {
    Find(ctx context.Context, tenantID, taskID string) (*task.Task, error)
    Save(ctx context.Context, task *task.Task) error
}

// postgres package: no "implements" declaration
type TaskStore struct { db *gorm.DB }
func (s *TaskStore) Find(ctx context.Context, tenantID, taskID string) (*task.Task, error) { ... }
func (s *TaskStore) Save(ctx context.Context, value *task.Task) error { ... }

// Optional compile-time documentation/check:
var _ application.TaskRepository = (*TaskStore)(nil)

A concrete type satisfies an interface automatically when its method set matches. This enables decoupling but creates a navigation gap. The compile-time assertion documents intent and fails early after signature changes.

Deep dive: pointer versus value method sets

Methods with receiver (t T) belong to both T and *T method sets. Methods with receiver (t *T) belong to *T. Therefore a value T may not satisfy an interface that requires a pointer-receiver method.

Interface design

Accept interfaces; return useful concrete types

Good port

type TaskFinder interface {
  Find(ctx context.Context,
    tenantID, id string) (*Task, error)
}
Small, consumer-specific, meaningful.

Leaky port

type Repository interface {
  DB() *gorm.DB
  Find(any) any
  Save(any) error
  // 22 more methods...
}
Infrastructure leaks in; callers depend on too much.

Do not create an interface merely because a type exists. Create it where an actual consumer needs substitutable behavior—testing, alternative infrastructure, or architectural isolation.

Construction

The composition root is the runtime map

func main() {
    cfg := mustLoadConfig()
    db := mustOpenDatabase(cfg.DatabaseURL)

    taskStore := postgres.NewTaskStore(db)
    clock := systemclock.New()
    taskService := application.NewTaskService(taskStore, clock)
    taskHandler := httpapi.NewTaskHandler(taskService)

    router := httpapi.NewRouter(taskHandler)
    runServer(router)
}

Construct from details inward, then expose outward. Constructors validate dependencies and make them visible. Avoid global service locators because they hide what a type needs and make tests order-dependent.

Package structure

Use boundaries, not ceremonial layers

internal/
├── task/                 # entities, statuses, transition rules
├── application/          # use cases + ports it consumes
├── adapter/
│   ├── httpapi/          # Gin DTOs, handlers, error mapping
│   └── memory/           # current repository adapter
└── platform/             # config, logging, clock implementations
cmd/api/main.go           # composition root

The internal directory prevents imports from outside the parent module. Avoid circular imports by making dependencies one-directional. If packages A and B need each other, the responsibilities or shared contract are probably misplaced.

Fakes and tests

Test use cases without infrastructure

type fakeTaskRepo struct {
    task *task.Task
    saved bool
    err error
}
func (f *fakeTaskRepo) Find(context.Context, string, string) (*task.Task, error) {
    return f.task, f.err
}
func (f *fakeTaskRepo) Save(context.Context, *task.Task) error {
    f.saved = true
    return f.err
}

A hand-written fake is often clearer than a generated mock for two-method interfaces. Test observable decisions: error returned, transition applied, save called. Do not encode the exact internal call order unless order is a real invariant.

Navigation drill

Resolve an interface call systematically

  1. At s.repo.Save(...), open the field’s interface definition.
  2. Write down the exact method signature.
  3. Use “Go to implementations” or search func (.*) Save(.
  4. Identify plausible adapters.
  5. Find NewTaskService( references.
  6. Inspect the startup/composition root to see the actual injected adapter.
  7. Repeat with a Governata interface call and draw the chain.

Knowledge check

1. Which package should normally define TaskRepository?

Show answer
The consuming application package, because it knows the minimum behavior it needs. The PostgreSQL adapter should satisfy that contract without owning it.

2. Why can a giant repository interface hurt?

Show answer
Consumers depend on unrelated methods, fakes become large, changes ripple widely, and infrastructure concepts leak into use cases.

3. What is the composition root?

Show answer
The startup location that creates concrete adapters/services and injects dependencies. It is the authoritative runtime wiring map.

Common traps

  • Inventing interfaces on the provider side before a consumer needs them.
  • Returning an interface from every constructor, hiding useful concrete behavior.
  • Adding layers that only forward arguments and express no boundary.
  • Letting handlers use GORM directly.
  • Using globals to avoid explicit constructor wiring.
