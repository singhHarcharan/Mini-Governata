Configuration

Fail fast before serving traffic

type Config struct {
    HTTPAddr    string
    DatabaseURL string
    NATSURL     string
    LogLevel    string
}

func Load() (Config, error) {
    cfg := Config{
        HTTPAddr: envOr("HTTP_ADDR", ":8080"),
        DatabaseURL: os.Getenv("DATABASE_URL"),
        NATSURL: envOr("NATS_URL", "nats://nats:4222"),
    }
    if cfg.DatabaseURL == "" { return Config{}, errors.New("DATABASE_URL required") }
    return cfg, nil
}

Parse once at startup, validate ranges and required values, and pass typed config to constructors. Secrets come from the runtime secret mechanism, never source or frontend builds. Log non-sensitive effective configuration so operation is explainable.

Use structured fields rather than formatted prose. Never use raw user IDs, task IDs, URLs, or error strings as metric labels—the cardinality explosion harms the monitoring system.

Metrics

Begin with RED and worker health

  • Rate: requests/messages/jobs per second.
  • Errors: failures by stable category.
  • Duration: latency histograms by route template/operation.
  • Saturation: DB pool usage, worker queue depth, consumer lag.
  • Reliability: outbox oldest age, retry count, DLQ depth, projection lag.

Prefer route templates such as /tasks/:id, not raw paths. Define alerts from user impact and sustained symptoms, not every single failure.

Instrumentation creates spans around meaningful operations. Propagators inject trace context into outbound HTTP/message headers and extract it on receipt. Correlation IDs support business-level tracking; trace IDs support telemetry. They may overlap but are not identical concepts.

Sampling means not every trace is stored. Do not rely on traces as the audit record.

Health and lifecycle

Alive is different from ready

ProbeMeaning
LivenessProcess is responsive; repeated failure may justify restart.
ReadinessInstance can accept useful traffic; dependencies/migrations/consumers are sufficiently ready.
StartupOptional protection for slow initialization before liveness enforcement.

On shutdown: mark not-ready, stop accepting work, cancel consumers/workers, drain within a deadline, flush telemetry, close clients. Shutdown must be bounded; perfection cannot hang deployment forever.

Containers

Build reproducibly; run minimally

FROM golang:1.26 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -o /out/api ./cmd/api

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/api /api
USER nonroot:nonroot
ENTRYPOINT ["/api"]

Pin versions/digests as your environment requires, run as non-root, keep secrets out of layers, and use multi-stage builds. In Compose, services reach each other by service DNS name, not localhost. A startup order is not readiness; clients still need retry/backoff.

Testing strategy

Prove each risk at the cheapest faithful layer

LayerProves
Domain unittransitions, deadlines, policy decisions
Adapter integrationSQL constraints/transactions, NATS semantics, object storage behavior
ContractAPI/event schemas between producer and consumer
System/E2Ecritical user journey across running services
Failure drillrecovery during real interruption/duplication/lag

High coverage is not the goal; high confidence in costly failure modes is. Make tests deterministic with isolated tenants/data, fixed clocks, and bounded waits rather than arbitrary sleeps.

Capstone drill

Diagnose one broken completion

  1. Start the complete-task action in React and note its request/correlation ID.
  2. Find the API log and trace; locate time spent and status category.
  3. Inspect the database transition/audit/outbox rows.
  4. Follow the published event and Governance/Core consumer lag.
  5. Check retry/DLQ and the affected projection.
  6. Explain the root failure, user impact, safe recovery, and prevention signal.
  7. Repeat the trace in real Governata and identify corresponding packages/configuration.

Knowledge check

1. Why not use raw task ID as a metric label?

Show answer
It creates unbounded unique time series (high cardinality), increasing cost and degrading metric storage/query performance.

2. Why can readiness fail while liveness succeeds?

Show answer
The process is alive but temporarily cannot serve useful traffic—perhaps DB connectivity, migration, or required consumer state is unavailable.

3. What is your first cross-protocol navigation key?

Show answer
Use request/correlation/trace identifiers at runtime; in source, use route paths, message subjects/event types, and composition wiring.
