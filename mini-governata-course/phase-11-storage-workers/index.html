What you will build

A user uploads evidence for a governance task. PostgreSQL stores metadata and relationships; object storage holds bytes; a worker checksums/scans/processes the object; Redis caches safe asset summaries. Failures leave recoverable status, not dangling mystery.

Use unguessable, tenant-prefixed object keys such as tenants/{tenant}/evidence/{id}; do not trust filenames as keys. Stream rather than loading entire files into memory. Enforce size and allowed content types, but do not trust declared MIME type alone.

Presigned URLs

Delegate bytes, keep authorization

A presigned URL grants temporary permission for one object operation. The API must authenticate the user, authorize task access, choose the object key and limits, and issue a short expiry. The browser uploads directly, then tells the API to finalize; the API verifies object metadata before marking it ready.

Treat a presigned URL as a short-lived bearer credential. Never log it or issue broad bucket access.

Cache-aside

Cache is an optimization with a stale-data policy

func (s *AssetService) Get(ctx context.Context, tenantID, id string) (*Asset, error) {
    key := "asset:v1:" + tenantID + ":" + id
    if asset, ok := s.cache.Get(ctx, key); ok { return asset, nil }
    asset, err := s.repo.Find(ctx, tenantID, id)
    if err != nil { return nil, err }
    _ = s.cache.Set(ctx, key, asset, 5*time.Minute) // cache failure is non-fatal here
    return asset, nil
}

On write, commit database truth, then delete/update the cache. TTL limits staleness; versioned key prefixes simplify format changes. Include tenant identity in keys. Do not cache permission decisions carelessly—revocation latency is a security property.

Deep dive: cache stampede

When a popular key expires, many requests may hit the database. Mitigate with TTL jitter, request coalescing/singleflight, stale-while-revalidate, or proactive refresh. Choose based on load and acceptable staleness.

Workers

Background does not mean unowned

type Job struct { EvidenceID, TenantID string }

func (w *Worker) Handle(ctx context.Context, job Job) error {
    meta, err := w.repo.Find(ctx, job.TenantID, job.EvidenceID)
    if err != nil { return err }
    reader, err := w.objects.Get(ctx, meta.ObjectKey)
    if err != nil { return err }
    defer reader.Close()
    digest, err := checksum(reader)
    if err != nil { return err }
    return w.repo.MarkProcessed(ctx, meta.ID, digest)
}

Jobs carry identifiers, not giant payloads. Workers refetch authoritative metadata, stream data, use timeouts, update status, and are idempotent. Set concurrency from downstream capacity rather than CPU count alone.

Failure design

Every partial state needs reconciliation

FailureRecovery
Metadata created, upload never occursExpire pending records and incomplete multipart uploads.
Object uploaded, finalization failsRetry finalize or sweep orphan objects.
Processing failsRecord failed status/error category; bounded retry.
Cache unavailableFall back to database if safe; observe degraded latency.
Delete partially succeedsTombstone metadata and retry object deletion.

Build sequence

  1. Add evidence metadata migration and states.
  2. Create an object-store interface and MinIO adapter.
  3. Implement authorized upload initiation/finalization.
  4. Stream and checksum an object in a cancellable worker.
  5. Add cleanup/reconciliation for pending and orphaned objects.
  6. Add tenant-safe cache-aside for asset summaries.
  7. Test cache unavailable/stale, interrupted upload, duplicate job, and large stream.

Knowledge check

1. Why not store file bytes in PostgreSQL here?

Show answer
Large blobs increase database backup, replication, memory, and query burden; object storage is designed for streamed immutable objects while PostgreSQL keeps transactional metadata.

2. Is Redis authoritative?

Show answer
Not for this design. It accelerates reads; PostgreSQL remains truth, so cache loss must affect performance rather than correctness.

3. What makes an upload recoverable?

Show answer
Explicit lifecycle states, stable IDs/keys, verification, idempotent finalization, and sweepers for abandoned/orphaned parts.
