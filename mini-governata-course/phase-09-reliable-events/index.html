The failure to understand

“Save task, then publish event” is two independent writes. A crash between them leaves durable state with no event. Publishing first can leave an event describing a state that never committed. Ordinary transactions cannot span PostgreSQL and NATS safely.

The API can return after the transaction commits. A worker publishes later. The outbox provides at-least-once publication intent; it does not remove duplicates.

Claiming

Let replicas share work without double-claiming

SELECT id, subject, payload
FROM outbox_events
WHERE published_at IS NULL AND available_at <= now()
ORDER BY occurred_at
FOR UPDATE SKIP LOCKED
LIMIT 100;

Workers claim rows inside a short transaction. SKIP LOCKED lets concurrent workers take different rows. Do not hold the database transaction open during network publication; use a lease/claim timestamp if publishing may take time, and reclaim expired leases.

The deduplication marker and business effect must commit atomically. Idempotency means processing the same message again produces no additional effect—not merely that the handler “usually” sees one delivery.

Retry policy

Retry transient failures; surface permanent ones

delay := min(base*time.Duration(1<<attempt), maxDelay)
jitter := time.Duration(rand.Int64N(int64(delay / 4)))
availableAt := clock.Now().Add(delay + jitter)
FailureAction
Temporary timeout/unavailable DBRetry with exponential backoff + jitter.
Invalid schema/versionDo not retry forever; quarantine/DLQ and alert.
Business rejectionRecord outcome; usually permanent.
Unknown failureBound attempts, preserve diagnostics, alert.

Jitter prevents many workers retrying simultaneously. A dead-letter queue is not a trash bin: define ownership, alerts, inspection, correction, and safe replay.

Concurrency

Goroutines need ownership and backpressure

jobs := make(chan OutboxEvent, 100)
group, ctx := errgroup.WithContext(ctx)

group.Go(func() error { defer close(jobs); return poll(ctx, jobs) })
for i := 0; i < workerCount; i++ {
    group.Go(func() error {
        for {
            select {
            case <-ctx.Done(): return ctx.Err()
            case event, ok := <-jobs:
                if !ok { return nil }
                publish(ctx, event)
            }
        }
    })
}
return group.Wait()

A goroutine is a lightweight concurrent function. A channel communicates values and applies backpressure when bounded. The sender owns closing the channel. Every goroutine needs an exit path; cancellation should reach blocking operations.

Deep dive: data races

A data race occurs when goroutines access the same memory concurrently and at least one writes without synchronization. Prefer message passing/ownership, or protect shared state with a mutex. Run go test -race ./....

Failure drills

Reliability is demonstrated by interruption

  1. Kill the API after task/outbox commit; prove event publishes after restart.
  2. Kill the publisher after publish but before marking sent; prove duplicate causes one consumer effect.
  3. Run two publisher replicas; prove claims do not starve or double-process normal work.
  4. Send a poison event; prove bounded retry and DLQ alert.
  5. Stop the database temporarily; observe backoff rather than a hot loop.
  6. Cancel the process under load; prove goroutines exit within the shutdown deadline.

Knowledge check

1. Does the outbox give exactly-once delivery?

Show answer
No. It prevents lost publication intent, but a crash around publish/mark-sent can duplicate delivery. Consumers still need idempotency.

2. Why atomically write inbox and projection?

Show answer
Otherwise the marker and effect can diverge, causing skipped work or duplicated effects after a crash.

3. What is backpressure?

Show answer
A mechanism that slows producers when consumers are at capacity, preventing unbounded memory/work growth.
